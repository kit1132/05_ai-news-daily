# daily-summary — AIニュース日次サマリー生成

## 目的

kit1132 の3つのソースリポジトリの当日ダイジェストを統合し、日次サマリー Markdown を生成して main に直接 push する。

## 前提

- タイムゾーンは JST（Asia/Tokyo）。当日日付 `<DATE>` は `TZ=Asia/Tokyo date +%Y-%m-%d` で取得する（`<YYYY>` = 年4桁、`<MM>` = 月2桁）
- 作業ブランチは必ず `main`。feature ブランチ・PR は作らない
- 入力リポジトリへは一切書き込まない（読み取り専用）

## 入力（読み取り専用・3リポ）

| リポ | パス | 更新時刻（JST目安） |
|---|---|---|
| `kit1132/01_ai-news-Master` | `digests/<YYYY>/<MM>/ai-news-<DATE>.md` | **当日 04:10 頃** |
| `kit1132/03_ai-news-industry` | `digests/<YYYY>/<MM>/ai-news-<DATE>.md` | **当日 05:10 頃** |
| `kit1132/02_ai-news-Copilot` | `digests/<YYYY>/<MM>/ai-news-<DATE>.md` | **当日 06:10 頃** |

※ 3ソースとも**当日の早朝**にコミットされる（本サマリーの 07:00 実行より前）。当日 07:00 の実行時点で当日分が無い場合、そのソースの当日早朝の実行が失敗している。

※ 2026-07-26 修正: 旧記載は「前日 19:10 / 20:05 / 21:05 頃」だったが、git のコミット時刻を実測した結果すべて誤りだった（実際は当日 04:13 / 05:10 / 06:10、直近7日で確認）。この表は生成エージェントが「欠損か未生成か」を判断する根拠になるため、時刻がズレると誤った欠損リカバリを走らせる。

## 手順

1. ブランチを main に揃える:
   ```
   git fetch origin main
   git checkout main
   git pull origin main
   ```
2. 出力先 `daily/<YYYY>/ai-news-daily-<DATE>.md` が既に存在する場合は、何も変更せず「本日分は生成済み」と通知して終了する（後述の欠損リカバリは実施してよい）
3. **欠損リカバリ**: 前日のサマリー `daily/<YYYY>/ai-news-daily-<前日DATE>.md` の冒頭注記に欠損ソースが記録されている場合、そのソースの前日分ダイジェストが現在は取得できるか確認する
   - 取得できる場合: 前日のサマリーを全ソースで再生成して**上書きする**（欠損リカバリに限り上書きを許可）。冒頭注記を「Nソース統合」に更新し、`Regenerate AI news daily summary for <前日DATE> (missing source recovered)` として当日分とは別にコミットする
   - 取得できない場合: 当日サマリーの改善メモに「<リポ名> の <前日DATE> 分は依然欠損（ソース側ルーチンの実行失敗の可能性、要確認）」と記録する
4. 3ソースの当日ダイジェストを読み取る。取得できないソースは「欠損」として記録する
   - **3ソース全欠損**: 生成を中止し、その旨を通知して終了
   - **一部欠損**: 取得できたソースのみで生成し、冒頭の注記に欠損ソースを明記
5. 下記フォーマットに従い日次サマリーを生成し、`daily/<YYYY>/ai-news-daily-<DATE>.md` に保存する
6. `files.json` の配列先頭に新ファイルのパス（例: `daily/2026/ai-news-daily-2026-06-13.md`）を追加する
7. コミット & プッシュ:
   ```
   git add daily/ files.json
   git commit -m "Add AI news daily summary for <DATE>"
   git push origin main
   ```
8. push 後、`git log origin/main -1` で main に反映されたことを確認する

## 出力フォーマット（日本語）

```
# AI News Daily Summary — <DATE>

（3ソースすべて揃った日は **冒頭注記を書かない**。欠損・リカバリがあった日だけ次の1行を置く）
> ※ <リポ名> は当日分が未取得のため N ソースで作成

## 今日のハイライト

最重要ニュース3件（下の「ハイライトの選定基準」に従う。該当が無ければ2件・1件でよい）。
各件は `### N. タイトル — 一言の含意` の見出しに続けて
**要点** / **詳細** の2段落で構成し、末尾に出典URLを箇条書きで付ける。

- **要点**: 何が起きて、**つまり前提が何から何へ変わったか**まで書く。**120字以内**。
  事実の要約で終わらせない。ここだけ読んで「読むか飛ばすか」を判断できるようにする
- **詳細**: 数値・スペック・日付・経緯。事実の裏付けを兼ねる

**書かないこと**:
- 一般論の助言（「〜を要件化すべき」「〜から着手するのが妥当」等）。読まれていないため2026-07-26に廃止した
- 材料がない段落を無理に埋めること。**該当する内容がなければその段落は省略する**

## カテゴリ別まとめ

ハイライト以外のニュースをカテゴリごとに箇条書きでまとめる。
カテゴリは当日のニュース内容に応じて柔軟に設定する
（例: Anthropic / Claude、OpenAI、Google / DeepMind、Microsoft / GitHub、
Copilot Studio / Power Platform、Cursor / 開発ツール、規制・政策、その他）。
重要項目には出典URLを付け、ハイライトで詳述済みの項目は「（ハイライト参照）」と書く。

## 直近の注目予定

今後の確定日付イベント（GA日、モデル退役日、カンファレンス等）を日付順の箇条書きで。

## 改善メモ

3ソースのダイジェストに含まれる改善メモ（取得失敗したソース、追加候補ソース等）を
引き継いでまとめる。ソース間の重複・矛盾に気づいた場合もここに記録する。
```

### 統合の方針

- 複数ソースで重複するニュースは1つに統合し、情報量の多い方をベースにする
- 矛盾する記述があれば両論併記し、改善メモに記録する
- URL は原文のまま記載する

## 冒頭注記は「変化があった日」だけ書く（2026-08-01 追加）

**3ソースすべて揃った日は、冒頭の `>` 注記を書かない。**

2026-08-01 の実測では、76日ぶんのうち**ソース欠損があったのは3日（4%）**しかなかった。
残る96%は「本サマリーは 01…・02…・03… の3ソース（M/D分）を統合して作成。」という定型文で、
375×812 のビューアで **86px（画面の10.6%）** を占めていた。読み始めるまでの距離を押し下げるだけで、
情報を持っていない。

書くのは次の場合だけ:

- いずれかのソースが未取得で、N ソースで作成したとき
- 欠損リカバリで再生成したとき（経緯を1行で書く）

⚠️ ビューア側は、注記に `※` / `未取得` / `欠損` / `取得できず` のいずれも含まれない場合、
その注記を圧縮表示する（`decorateNote`）。**この4語のいずれかを必ず入れること。**
入れ忘れると、読ませたい欠損の情報まで小さく表示される。

## ハイライトの選定基準（2026-07-31 追加）

**「最重要」の定義が無かったため、同じ日の同じ入力から違う顔ぶれが選ばれていた。**
2026-07-31 のサマリーには2つの版が存在し、3件目が「Claude 共有リンクの検索エンジン露出」と
「Power Automate 3機能の GA」で割れていた。基準を以下に固定する。

次のいずれかに当たるものだけをハイライトにする。該当が3件を超える場合は **1 → 2 → 3 の順**で採る。

1. **不可逆な期限がある** — 退役日・廃止日・ポリシー発効日など、見逃すと取り返せないもの
2. **前提が壊れた** — 価格・仕様・可用性が変わり、既存の試算や提案を引き直す必要があるもの
3. **今日から手が動く** — kit が使っているツール（Claude Code / Copilot / Cursor / Power Platform / AWS）の
   挙動・権限・料金が変わり、当日から操作や設定が変わるもの

**ハイライトにしないもの**（カテゴリ別まとめに置く）:

- 「更新なし」「据え置き」「変化なし」の報告。変化がないものに so what は無い
- **既報の再掲**。一度ダイジェストに載せた話題を、続報なしで再びハイライトにしない。
  ⚠️ **「出来事が古いこと」と「既報であること」は別である。**発生が2週間前でも、
  **本日はじめて判明した事実**はハイライトの対象にしてよい（例: Release Wave の緑チェックだけが
  一次シグナルで、GA から2週間後に検知した機能）。除外するのは既に載せた話題の蒸し返しだけ
- 公式未確認の観測・推定だけで成り立つ話題

該当が1件も無い日は、**2件・1件に減らしてよい**。件数を埋めるために基準を緩めない。

## 「意味」段落の廃止（2026-07-31）

so what を400字超の「詳細」の後ろに置くと、結論が壁の向こう側になって読まれない。
2026-07-31 実測では要点93字（事実の要約のみ）→詳細435字→意味237字（so what）の順で、
結論に辿り着くまでに528字を読ませていた。so what は要点に統合する。

**要点の80字→120字はこの統合ぶんの増枠であり、詳細を水増ししてよいという意味ではない。**
統合した so what は「前提が何から何へ変わったか」であって「〜すべき」ではない。
2026-07-26 に廃止した「行動指針」を名前を変えて復活させないこと。

## ハイライト形式をカテゴリ項目に広げない理由（2026-07-31）

**`**要点**` / `**詳細**` のラベルはハイライトにだけ付ける。カテゴリ項目には付けない。**

カテゴリ項目にも「結論を先に、裏づけを後に」の構造は**既に入っている**
（第1文ルール 2026-07-28、列挙の外形化 2026-07-31）。違いは `**要点**` / `**詳細**` のラベルを貼るかどうかだけである。
それでもラベルを貼らないのは次の2点による。

1. **序列が消える** — `.lbl` のラベル列と左の色罫は、ビューア上でハイライトを他と区別している唯一の装置である。
   全項目に付けると「今日の N 件」が同じ見た目のブロックに埋没し、どれを先に読むかが分からなくなる
2. **縦幅が増える** — 2026-07-31 の実測（375×812・全節開・05 daily の公開版）で、カテゴリ親項目20件に
   要点/詳細を貼ると **+1.8画面**（18.5 → 20.3画面・+10%）。モバイルはラベルが縦積みになるため1個あたり37px 効く

⚠️ 旧根拠「全項目を段落形式にすると 01 で3.0倍・02 で2.2倍に膨らむ」（2026-07-26 実測）は
**要点/詳細/意味 の3段落時代の測定**であり、「意味」を廃止した 2026-07-31 以降は当てはまらない。
2026-07-31 に上記の理由へ差し替えた。

## 列挙の外形化（2026-07-31 追加）

**地の文に並列列挙が3つ以上現れたら、ネストした箇条書きに外形化する。**

これまでのルール（太字・第1文）はすべて *文レベル* の規定で、**構造レベルの規定が1つも無かった**。
そのため列挙が地の文に埋め込まれたままになり、読み手の目が休まる場所が無くなっていた。

### 判定シグナル（どれか1つでも当たれば外形化する）

- `①②③` のような丸数字を使っている（記号を使った時点で、書き手は列挙だと自覚している）
- 中黒 `・` で3語以上を連ねている
- 読点 `、` で並列句を3つ以上連ねている

### 書き方

- 親行に「何が公開された/変わったか」を書き、内訳を子行に落とす
- 各子行は **識別子: 中身** の形にする。機能名・API 名・製品名を行頭に出すと目が拾える
  - ⚠️ **バッククォートで囲むのは英数字の識別子だけ**（`EmailActions`・`embedded_resource_snapshot_id` 等）。
    **日本語の見出し語は囲まない。** `code` は等幅フォントに切り替わり、日本語が混じると環境によって
    明朝系にフォールバックして本文（ゴシック）と書体が混在する（2026-07-31 実測・8箇所で発生）
  - 日本語の見出し語は**装飾なしで行頭に置く**。行頭にあること自体が目印になるので太字も不要
    （太字は「1項目3箇所まで」の枠を食う）
- **1項目1行に機械分割しない。** 序列の低いものはまとめて1行にする

### 目的は字数削減ではない

外形化しても字数はほとんど変わらない（下の例で約230字→約250字）。
**改行が「並列であることの合図」と「目の休憩場所」を同時に作ることが目的**である。
字数を理由に外形化を見送らないこと。

2026-07-31 の実測（直近7日・80字超の項目）では、地の文に3連以上の並列列挙が埋まっているものが
daily 39/196件（20%）・Master 17/63件（27%）・Copilot 12/111件（11%）あった。

```
（悪い）
- 拡張機能 What's New に「July 2026」節が新規追加。①`EmailActions` 機能（メールのトリアージ・監督付き送信・削除・受信ルール・自動応答・フォルダー管理の書き込み操作）、②`MeetingActions` 機能（会議のスケジュール・時間調整投票・時間インサイト）、③ワーカーエージェントを `id` の代わりにファイルパス（`file` プロパティ）で参照可能に、④埋め込みナレッジに `embedded_resource_snapshot_id` を追加。あわせて Copilot 利用状況レポート API 3種に `version` パラメーターが追加された。

（良い）

  - `EmailActions`: メールのトリアージ・監督付き送信・削除・受信ルール・自動応答・フォルダー管理の書き込み操作
  - `MeetingActions`: 会議のスケジュール・時間調整投票・時間インサイト

  - Copilot 利用状況レポート API 3種に `version` パラメーターが追加された
```

## 第1文の書き方（主体と述語）（2026-07-28 追加）

カテゴリ別項目の**第1文は、それ単独で意味が通る完全文にする**。

⚠️ **このルールが掛かるのは説明側だけである。**見出しに相当する部分
（`**ラベル**:` のラベル、`タイトル — 説明` のダッシュより前）は文ではなくラベルなので、
`Agent 365 の新規購入に前提ライセンスが必須化（6/1 発効）` のように体言止めでよい。
述語で終える必要はない。

- 第1文（説明側）は「〈主体〉が〈何を〉〈どうした〉」の形にし、**述語（動詞・助動詞）で終える**
  - 禁止: 「〜可能に。」「〜追加。」「〜対応。」「〜開始。」のような体言止め
  - 可: 「〜できるようになる。」「〜を追加した。」「〜に対応した。」
- 主体が2つある場合は**操作・受益主体を優先**する
  - 操作・受益主体 = 誰が設定するか / 誰が使えるようになるか（開発者・管理者・エンドユーザー・対象プラン）
  - 発表主体 = 誰が出したか（Anthropic / OpenAI / Microsoft 等）。
    **本サマリーは3ソースを横断するため発表主体は原則として省略しない**
- 太字ラベル（`**機能名**:`）は残す。ただしラベルは *モノの名前* であって主体ではないので、
  **ラベルがあっても主語を書いたことにはならない**。ラベルを隠しても第1文だけで通じること
- **例外**: 「（ハイライト参照）」だけの行はこのルールの対象外。ハイライトで詳述済みのため短縮してよい

**適用除外**: 「直近の注目予定」など将来日付のイベントを日付順に並べる節。

```
（悪い）Office アドインの統合マニフェストが GA（7/17）— Word / Excel / PowerPoint が Outlook に続いて対応。
（良い）Office アドインの統合マニフェストが GA になった（7/17）— Word / Excel / PowerPoint が Outlook に続いて対応した。

（悪い）Opus 5 のサイバー系ポリシー — ソースコード上の脆弱性発見は許可、バイナリ走査・侵入テスト・エクスプロイト生成はブロック。
（良い）Anthropic が Opus 5 のサイバー系ポリシーを線引きした — ソースコード上の脆弱性発見は許可し、バイナリ走査・侵入テスト・エクスプロイト生成はブロックする。
```

2026-07-27 の実測（各ソース最新10ファイル・ハイライト・改善メモ・日付一覧を除く）では、
**主語よりも「述語で終わらないこと」が壊れていた**。

| ソース | 項目数 | 主語あり | 述語で終わる | 両方満たす | 項目平均字数 |
|---|---|---|---|---|---|
| Master | 46 | 54% | 26% | 22% | 306字 |
| Copilot | 108 | 44% | 31% | 11% | 154字 |
| industry | 70 | 46% | 16% | 14% | 134字 |
| weekly | 580 | 33% | 6% | 2% | 113字 |
| **daily** | **116** | **51%** | **26%** | **17%** | **197字** |

主語（〜が / 〜は）は33〜54%残っているのに、述語で終わるのは6〜31%しかない。
主体を書いても体言止めで終えると「結局どうなったのか」が宙に浮くため、**両方**を守ること。

⚠️ **文字数と引き換えにしない。** このルールは文を長くする方向に働く。
「冗長な前置き不要」は引き続き有効で、**項目平均字数 236字（＝適用前197字の+20%）を超えたら書きすぎ**。
02 Copilot に先行適用した 07-28 分では、述語で終わる率 31%→91% に対し項目平均字数は 154字→155字（+0.6%）だった。
**文字数を増やさずに達成できる**。測定は `scripts/measure-subject-rate.py`（01_ai-news 親ディレクトリ）で行う。

## 太字（`**...**`）の使い方

太字は「あとで検索・引用したくなる語」だけに使う。**文や節をまるごと太字にしない**。

- **1項目（`###` 単位）につき太字は3箇所まで**
- **1箇所は20字以内**の語句に限る。それを超える長さは太字にしない
  - ⚠️ **例外: 固有名詞そのもの**（製品名・ページ名。`M365 Copilot Release Notes`・`GitHub MCP と Playwright MCP` 等）は
    20字を超えてよい。禁止したいのは「文・節をまるごと太字にすること」であって、名前が長いことではない（2026-07-31 追加）
  - **述語で終わる文は太字にしない。** 項目の見出しを結論の文にする場合は太字ではなく ` — ` 区切り
    （`結論の文 — 説明`）を使う。ビューアはダッシュの手前を見出しとして立てるが、20字超の太字は逆に
    ウェイトを落とす処理（`decorateBold`）に掛かり、**結論が弱く表示されてしまう**
- 対象は固有名詞＋バージョン（`Claude Code v2.1.220`）、金額（`$100M`）、日付、`%` などの数値
- 強調したい主張は太字ではなく**文の順序**（結論を先に書く）で示す
- 目安: 本文の太字比率は **10%以下**

2026-07-26 の実測（各ソース最新10ファイル・改善メモ除外）では、太字が
「多すぎる」と「1回が長すぎる」の2つの形で崩れていた。
